# Roster values: every vehicle, gadget and vehicle equipment stat entry (L3307)

Build 1.4.3.5, game head 4909067. Research only: no site data, simulation or UI change is authorized by this page.

The game keeps three stat rosters under `Persistence/StatCategories/StatCategorization`: 33 vehicles, 68 gadgets and 66 vehicle equipment items. This page records, for each of the 167 entries, what the saved game data stores about it. The full data is in `reference-data/frosty/roster-values.json` (one line per entry); the tables below are a reading aid generated from it.

## How the values were found

`scripts/frosty-roster-values.py` does the whole job in one pass over the saved raw assets:

1. It reads each roster entry's stat name, index, category pointers and GUID list.
2. It finds the object whose own GUID is in that list (the entry's defining object, usually an unlock) and every other saved file that contains one of the GUIDs.
3. A file that names only this entry is a carrier (an ability, equipment or passive-ability file). A file that names several entries is a shared user, almost always a vehicle blueprint; there the walk starts only from the objects that point at this entry (weapon mounts).
4. From those starting objects it follows pointers, inside the file and across files, up to eight steps, and records the damage, blast and projectile fields it reaches, with the file offset of every value ("own" values).
5. It joins named registry rows (`GRX_Gadgets_Glacier`, `GRX_Vehicles`) whose owner name equals the name of a reached file (`ownerName`), and rows listed for the entry in `reference-data/frosty/roster-registry-name-joins.json` (`nameTable`, a hand-reviewed match on names alone).
6. For a carrier file it also records every other plain number by field hash (`carrierUnnamed`); these have no known name.
7. For a vehicle it lists the equipment its blueprint mounts and the entries reachable from each `VehicleCustomizationContext_*` file that imports the blueprint.

Checks: 11,854 raw-offset checks over 470 files, all matched (`raw-checks.json` in the run folder). Three files failed to decode and are not used: two `SP_SwitchbladeDrone` damage affectors and `Affector_Damage_Exit_Crouched_IncendiaryGrenade`.

## What the evidence does and does not show

- A stored value proves neither its unit nor that a live match uses it. Nothing here is a damage, range or time claim about play.
- "reg" is a registry row's default; "own" is the field in the asset itself. They are recorded separately. They agree for 1,394 owner-and-property pairs and differ for 73 (`reference-data/frosty/roster-registry-vs-own.json`). Which one a live match uses is open question 1.
- An `ownerName` join rests on the registry owner having the same name as a reached file. A `nameTable` join rests on names alone. Neither is an asset reference.
- Display names: gadgets and vehicle equipment are joined to UI text by hand tables on names (`reference-data/frosty/roster-display-names.json`); no asset reference links a vehicle UI record to an equipment entry (the 183 UI record GUIDs occur in no non-UI saved file). Vehicle names join a UI record to the blueprint whose file name ends with the record name.
- A vehicle's blueprint values include every weapon and explosion object in that blueprint, so a vehicle row mixes its weapons. Read weapon values on the equipment rows.
- The walk can reach files shared between related entries (the three M320 launchers share a weapon blueprint), so a row can list a sibling's values. The headline column shows up to four distinct values per property; the JSON has the file for each.
- "Covers" lists which kinds of value were found for the entry by property name: damage, blast, projectile, ammo, reload (including rate of fire and heat), cooldown, range, duration, durability.

## Open questions and the in-game test for each

1. **Registry default or own value?** 73 properties differ. Tests, each in a private match with one clean hit on a full-health target, reading the damage number:
   - AT mine under a stationary empty tank: registry 195 against own 300 blast damage.
   - Javelin direct hit on a tank side: registry 140 direct and 155 blast against own 150 and 125.
   - M320 thermobaric at a soldier's feet: registry 50 against own 30.
   - MBT APFSDS on a soldier at under 50 m and at 350 m: registry 130 falling to 115 between 100 m and 300 m against own 150 falling to 135 between 50 m and 400 m. The distance pair alone separates the two.
   - RPG flight time over a measured 200 m: registry speed 70 with drag 0.004 against own 350 with no drag.
   - AA gun AAAP round on a soldier: registry 20 against own 57.
2. **Vehicle damage multipliers.** EA's tank numbers divide the registry value by whole numbers (RPG 500 = 125 x 4, APFSDS 650 = 130 x 5). Test: fire the same RPG at a tank's front, side and rear and at an IFV, and compare each number to 125 and to 135.
3. **Units of rate of fire and reload.** `RateOfFire` 900 with `MagazineCapacity` 1 and `ReloadTime` 4.1 for the MBT gun. Test: time ten shots with a frame-counted recording; 4.1 s per shot confirms reload time is seconds and that rate of fire does not bound the gun.
4. **Ability times.** `ActiveTime` / `RechargeTime` such as 5 / 32 for the tank intercept system and 8.1 / 16 for the smoke generator. Test: record the HUD from activation to ready and compare with active plus recharge.
5. **Passive upgrade sizes.** Field Maintenance rate 132 with delay 9.5 (IFV 110); Medbay 20 per interval 0.9 within 12.5; Enhanced Loading 1.35 below a 0.6 health threshold. Tests: damage a tank, stop, and time first heal tick and health per second; stand at 12 m and 13 m from an APC with Medbay; time reloads above and below 60% health with and without the upgrade.
6. **Auto-replenish.** `AutoReplenishDelay` and `AutoReplenishMagazine` on vehicle weapons. Test: empty a magazine pool and time each returned magazine.
7. **Lock-on rows.** `LockTime`, `UnLockTime`, `ReleaseTime`, `MinimumRange` on the 14 locking controllers, default against painted. Test: time the lock tone on an unpainted and a laser-painted helicopter at a fixed range.
8. **Blast shape.** `InnerBlastRadius` against `BlastRadius` with `MinimumBlastDamage`. Test: detonate C-4 at 1 m, 2 m and 3 m from a soldier and compare with full damage inside 1 and a fall to the minimum at 3.
9. **Vehicle disable thresholds.** `DisabledDamageThreshold`, `ClearDisabledDamageThreshold`, `RepairRateModifier` on blueprints. Test: reduce a tank to just above and just below the threshold and note when the mobility penalty starts and clears.
10. **Unnamed numbers.** The radar multipliers 1.5 and the guided-shell numbers 30, 6, 0.3 and 150 have no names. Test for radar: compare minimap detection range for an attack helicopter with and without Radar System.
11. **Which entries are live.** `veh_air_mh350`, `veh_breacher`, `vehec_wp_30revcan`, `veheq_eq_airrevive` and the nine unused gadget tree leaves have no assets. Test: none needed unless the id appears in GameTools data or a patch adds assets; recheck after each update.
12. **Gadget counts and cooldowns.** `NumberOfMagazines`, `MagazineCapacity` and replenish rows for throwables and launchers. Test: count carried items at spawn and time the resupply from a supply bag.

## L3314 - Registry default or asset value: stored links and update history (9 October 2026)

[Receipt](../../reference-data/provenance/frosty-2026-10-09-L3314-registry-vs-asset.json). Dataset: `reference-data/frosty/registry-vs-asset-evidence.json`. This bears on open question 1 above; it does not settle it.

What is stored:

- **The registry points at assets by GUID.** Container rows of `GRX_Vehicles` and `GRX_Gadgets_Glacier` (315 rows) reference a small object holding a GUID string. 57 of the 96 distinct GUIDs are instance GUIDs of objects in saved gameplay files.
