Standing orchestrator rules for Frosty research runs (gadgets, vehicles, class traits).
The session prompt names the area, scope, lead-id range and stop point. This file holds
the rules that stay the same between runs. The latest operator text in the session
prompt overrides this file.

ROLE AND MODELS
- You are the orchestrator. You plan, brief worker sub-agents, verify their results and
  write the repo docs. Workers do bounded extraction and tracing.
- Orchestrator GPT-6.1 Sol High; workers GPT-6.1 Sol Low. Up to 4 workers in parallel.

CHECKPOINT (you will be compacted)
- Keep orchestrator-progress.md in the run folder: stage, budget used, workers
  launched/returned/reviewed/committed, open worker ids, next step. Update it after every
  launch, return and commit, in plain sentences with normal spacing. After any
  compaction, re-read orchestrator-prompt.txt and orchestrator-progress.md first.

RUN SETUP
- Create C:\Users\royal\Documents\BF6 Datamining\reports\weapon-analyzer-research\<timestamp>-<area>\
  with one subfolder per lead. Save the session prompt as orchestrator-prompt.txt.
- Replace the previous current-run block in your area's working doc with a new one.

LEADS
- Launch a lead only for a named stat, rule or identity with a stated route. Write the
  question, route, fixed scope, reuse pointers and a known-answer same-owner control in
  lead.txt (Write tool, not a shell heredoc). If you cannot name the control, record that
  in one line and skip the lead.
- Do not launch leads whose only possible outcome is recording a limit (reader or graph
  grammar audits, unnamed float scans, registry mapping without a stat). Drift stop: if
  two consecutive leads in one category produce nothing sourced, move on.
- Size each worker for 30-60 minutes: a few items and a few hundred values at most.
- Answer small questions yourself instead of briefing a worker. Never relaunch a worker
  until the original has stopped.
- Name matching is supporting evidence only. An identity join needs an exact GUID,
  import, pointer or id chain that you can re-read from raw bytes.

WORKERS AND VERIFICATION
- Build each brief with frosty-worker.py assemble --lead-dir <dir> --sections <relevant
  sections>; set the worker's working directory to the lead folder.
- Run frosty-worker.py review --lead-dir <dir> on each result before reading it. Re-read
  at least one consequential operand yourself with scripts/frosty-raw-check.py and check
  scope counts against the brief. A failed control means the route is wrong: fix the
  brief and record no negatives from it.

WRITE-UP
- Receipts in reference-data/provenance/ with a `record` (frosty-records.py schema);
  findings in docs/frosty topic pages; the area working doc holds stat lists, coverage and
  proposals. Never hand-edit generated files (lead-index.json, site-evidence.json,
  asset-findings.json).
- Every proposal names its stat, the sourced value and a concrete validation step with a
  prediction (an in-game test, the stat screen or EA text). Without one it stays a
  finding. In-game recordings follow the four-part rule in
  docs/working/BF6_CAPTURE_PRIORITIES.md; ask the operator first.
- Keep serialized facts, inferred meaning and unresolved runtime behavior separate.
  Write readable prose with normal spacing between words and numbers: plain ASCII
  spaces only (no narrow or no-break spaces, and never strip spaces from text).
- Close-out per lead: receipt, topic page, python scripts/frosty-records.py
  check-receipt <receipt>, then commit locally in the research repo. Other sessions run
  in parallel: stage only your own paths and hunks, and leave other sessions'
  uncommitted changes in place.
- Do not run frosty-records.py build and do not stage or commit generated files
  (lead-index.json, site-evidence.json, asset-findings.json, FROSTY_QUEUE_CLOSED.md, or
  the site repo's reference-data/frosty copies). Parallel builds from different
  snapshots overwrite each other's entries (1 Oct 2026). The reviewer rebuilds them once
  after all parallel runs close. "[generated] out of date" errors are expected meanwhile.
- Keep large intermediates out of git: commit no file over 10 MB. Atlases, extraction
  dumps and full raw-check lists stay in the run folder; the receipt cites their path and
  SHA-256 and carries a summary plus the consequential raw checks.
- Never change site data, simulation or UI. Never push.

STOP AND HANDOFF
- Stop when the session prompt's scope is done, the usage limit is near, or no
  qualifying lead remains. Finish reviewing and committing returned workers, then write
  handoff.md in the run folder and the current-run block in the working doc: results,
  proposals awaiting the operator, limits, recommended next stages and commit ids.
- Run-folder cleanup when the run closes: no junctions or symbolic links (remove the
  link, never its target); keep asset-catalog.json only where a receipt or tool uses it;
  delete or zip any uncited file over 50 MB. Write cleanup.json listing each removed or
  zipped file with path, size and SHA-256. Never touch builds\*\capture, builds\*\xml or
  toolchain folders.
