Reading the evidence

The vehicle research traces configuration, not a validated vehicle simulator. Health, weapon choice, station ownership, default loadout, material interaction and native damage are separate questions. Matching a field name does not close all of them.

Read a value together with its owner, build, descriptor and selection route. A familiar field name or an identical number on another object is not enough to transfer its meaning.

EvidenceWhat it establishesWhat it does not establish
Stored game valueAn exact field on the selected serialized owner.Does not by itself establish activation, effective units or the native operation.
Source mappingA field name or association qualified by its declaring class, descriptor key and member schema.Schema-based name transfer is distinct from an inherited value and from native execution.
Rule read from a compiled graphA condition, constant or arithmetic step read from a compiled expression graph (the logic the game runs for a vehicle or ability), with the graph named in the lead.Constants imported from tunables are shipped defaults that the game can override remotely. Function meanings are named from use. Roles marked inferred are not read from the graph.
Inherited / registry defaultA base-class value or a named registry leaf, identified separately in the text.Never silently replace or average with the selected export’s own value.
Game description / UI summaryThe named card or menu statement; summaries retain their summary label.Does not establish a gameplay measurement or an exact UI-to-gameplay asset join.
EA patch notesAn EA statement at the explicitly cited update version.Does not prove the saved game build still behaves that way.
InterpretationA proposed explanation, correspondence or hypothesis.Does not establish a native equation or validated gameplay effect.
Analyzer modelA rule or calculated output in the pinned Analyzer software.Source-backed inputs do not automatically validate the software equation as native behavior.
In-game observationThe specifically cited game capture or test.Its result retains its weapon, loadout, build and measurement scope.

The colors identify the kind of evidence, not a confidence score. Field names, values and interpretations retain the qualifications beside them.

Null, zero, false and −1 are different observations. Do not turn an absent boxed default into zero, interpret −1 as “infinite,” or add the members of an unnamed tuple. “No join found” describes the checked scope, not proof that a feature does not exist.

Roster values and registry versus file values

Stored game value L3307 traced every stat entry of three rosters (167 entries across vehicles, vehicle equipment and gadgets) from its GUID list to its defining object and carrier files. A vehicle weapon’s firing and projectile data is linked inside the vehicle blueprint: the blueprint object that imports the equipment’s unlock also points at the WF_Vehicles_* weapon data. Ammunition types, upgrades and abilities sit in Eq_Vehicle_*, PassiveAbility_*, Ability_* and WMD_Vehicle_* files, and each VehicleCustomizationContext_* file imports one blueprint and the abilities offered on it.

  • Vehicles (Categorization_Vehicles, 33 entries): 31 have a defining object and own values, 30 have registry rows, 24 have a UI name.
  • Vehicle equipment (Categorization_Vehicles_Equipment, 66 entries): 64 have a defining object, 42 have own values, 60 have registry rows, 58 have a UI name.
  • No value of any kind: veh_air_mh350, veh_breacher, vehec_wp_30revcan and veheq_eq_airrevive (no saved file contains their GUIDs), and veheq_upg_imparm (its effect asset stores no plain number). Across all 167 entries, 157 have at least one stored value.
  • Registry default and own value agree for 1,394 owner-and-property pairs and differ for 73, most of them vehicle weapon damage and falloff (for example tank APFSDS start damage 130 against 150, falloff 100 to 300 against 50 to 400).

Passive-upgrade and ability rows are joined by a hand-reviewed name table, and equipment UI names by a hand table on designation text. Units and runtime use are unconfirmed. 11,854 raw-offset checks over 470 files matched.

Registry default Which value is live. Registry rows are bound to assets: 9,430 imports in 634 files point from an asset to a registry row, 869 to value rows (the registry is the stored source) and 8,561 to container rows carrying the asset’s own name, and for all 73 differing properties the owning asset imports its registry container (L3316). Over builds 1.4.2.5 to 1.4.3.5 ten registry rows changed; the scout helicopter minigun heat row changed in the registry only (0.006667 to 0.008889, asset still 0.006667), and EA’s 1.4.3.0 notes state a rise of about 33% (L3314, L3317). The evidence since then points one way:

  • Damage: registry defaults reproduce every EA damage figure checked for 16 weapons, including five changed in 1.3.3.0; the asset value gives the figure from before the change for tank APFSDS and the tank Aim-Guided Shell (L3324, L3339). EA’s blast radii follow the registry (L3318). 26 of the 73 differing properties are settled this way (L3327); 7 have an official number following the registry and 66 have none, so source data cannot settle those (L3319).
  • Non-damage: in 8 of 8 cases where EA states an old and new number and registry and asset differ, the registry default is the new number (L3356).
  • Exception: vehicle heavy machine gun muzzle velocity, where the file holds EA’s new figure (see “File values against registry rows”).
  • One user-reported in-game reading, an RPG on a tank’s rear dealing 500, follows the registry (Damage 125 gives 500; the asset’s 135 would give 540). It is one reading without a recording; build, tank type, range and health were not recorded (L3326). A recorded test from 9 November 2025 (M15 mine 770, SLAM 262 to 436, PTKM-1R 476) predates EA’s 1.3.1.0 change (L3320).

Interpretation Taking the registry default as the live value is an inference supported by these cases; no stored field proves it, and only an in-game reading can settle a property that has no official number. Eleven selected vehicle declarations also keep their three-field float32 tuples with exact parent imports (L3305); their roles and runtime effects are unknown.

Stored health, regeneration and critical thresholds

EA patch notes EA’s 1.3.1.0 notes state that tank health is 1200 and armoured transport health 800, and that weapons no longer deal different damage to IFVs, tanks, armoured transports and anti-air vehicles (L3334). Stored game value Both numbers equal the stored root health: Abrams and Leopard 1200, JLTV and Marauder 800. Bradley, CV90 and Gepard store 1000, which EA does not state. All seven damage-zone files store target material 119. The 1000-health premise for tanks used in earlier counts therefore no longer applies. For vehicles EA does not name, root health stays “configured, not proved effective”.

Stored game value Regeneration. Delay and rate are stored on the vehicle root object (Class_f2a56983, beside root health): Field_5c9d2d82 is the delay in seconds and Field_3233bcbf the rate in health per second (L3346). The CB90’s registry rows RegenerationDelay 12 and RegenerationRate 100 hold the same numbers as its two fields, which names them. EA’s 1.3.1.0 notes give a delay of 6 to 12 seconds and a rate of about 5% to 10% per second.

Stored game value Critical (disabled) thresholds. The CB90’s registry rows DisabledDamageThreshold and ClearDisabledDamageThreshold are both 400 and its root holds 400 in exactly two fields, Field_1a7c18f1 and Field_6497ebc7 (L3347). 23 vehicles have the same two registry rows, always equal to each other and to the root’s Field_6497ebc7: 400 for the two tanks and the CB90, 500 for the UH60, 300 for all others (L3348). The root’s Field_1a7c18f1 holds a lower number on 19 of them (200 on the tanks, 250 on the UH60). With registry defaults in use there is one threshold, and a tank is critical below 400 health, one third of 1200. This replaces the 200-and-400 reading offered in L3347. Whether the registry or the root field applies in a match is the same own-versus-registry question as elsewhere in this guide and is unmeasured. That the row name “disabled” is EA’s “critical health” is a join by meaning. RepairRateModifier is 1.0 on every vehicle with a row.

What the compiled expression graphs show

Rule read from a compiled graph An expression graph is the compiled logic a vehicle or ability runs. Four reads on 10 October (L4031, L4032, L4033, L4037) decoded them with exgraph.py; detail is in the run folder. One graph per driving class was read in full (JLTV, Abrams, F-16, AH-64) and compared with siblings by imports and constants; all 93 shared vehicle listings were read; the CB90, jet ski, Phalanx and small stationary graphs were read in full and the RHIB compared by imports. The driving and boat graphs are locomotion and aiming simulations only: health, damage thresholds, repair, seats, ammunition, overheat and countermeasure timers are not in them.

Caveats. Graph constants imported from tunables are the shipped defaults (L4034 lists 901 tunables read by simulation graphs, with default, minimum and maximum); the game can override them remotely. Function meanings are named from use, for example c07cd1f5 as float not-equal; none of 33,083 candidate names under four hash functions matched an identifier and the graph source assets hold no node list (L4036). Roles marked “inferred” below are not read from the graph. Decoded effect-asset values (L4035, 208 effect assets named by graphs) are stored values; which graph applies them is read from the graph.

Vehicle mobility hit rule

Rule read from a compiled graph SimEx_Vehicle_MobilityDamage was read in full (L4037). The registry rows are MobilityHitDamageThreshold 0.5, MobilityHitDuration 5 s and MobilityHitTimeFrame 3 s (L3312).

  • Trigger (0x214 to 0x414): for each new damage event with damage above 0, sum = damage + stored sum. If the sum is at least scale × MobilityHitDamageThreshold, Affector_Vehicles_MobilityDamage is applied for MobilityHitDuration and the sum is set to 0; otherwise the sum is stored.
  • Window (0x55c to 0x678): the sum is set to 0 when the ticks since the recorded hit exceed MobilityHitTimeFrame / max(frame time, 1/240).
  • Removal (0x438 to 0x4ec): Affector_Vehicles_RemoveMobilityDamge is applied when Vehicle Health Normalized equals 1 and a stored flag is set.
  • Scale: it is probably maximum health, but the graph does not identify it. If it is, a hit needs damage worth half of maximum health inside the time frame (inference, unmeasured).
  • Effect by class (L4031, L4033): tanks lose speed and turning, boats lose thrust, helicopters have two flight parameters halved, and jets get random roll and nose-down pitch.
  • Vehicle health and critical-health thresholds are not in expression graphs; they remain as recorded under “Stored health, regeneration and critical thresholds”.
