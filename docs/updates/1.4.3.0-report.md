> Copied on 14 October 2026 from `BF6 Datamining\builds\1.4.3.0\capture\CHANGE_REPORT.md`

The executable file-version string decreased while the hash changed. Do not use that
string to order builds.

**The SDK binary is the same, but the decoding is not equivalent.**
`SharedTypeDescriptors.ebx` changed with this build (`640de7ae…2ca13` to
`91c9ea7c…565c2`), so 108 type GUIDs moved and Frosty could not load an object in 341 of
the 835 exported assets. **That gap is now closed**: `scripts/frosty-ebx-decode.py`
decodes EBX straight from each build's own descriptors and does not use the SDK at all.
All 341 were decoded in both builds and compared. See *Decoding without the SDK*.

**`WPM_UBL_M320TB` traced; the first-pass reading was wrong.** This is not muzzle

not a balance change. The field's semantic name is still unknown.

### Interdictor (Desert Tech HTI)

Every item in the Interdictor patch notes maps to source evidence. The weapon blueprint
itself changed **only** muzzle-flash FX references; the damage work is in the bullet
assets and the material grid.

`Common/Hardware/Weapons/_Bullets/PD_.416Barrett`, curve `ba0c9abc`, distance/damage pairs:

| | 1.4.2.5 | 1.4.3.0 |
|---|---|---|
| | 100m → 80 | 100m → 80 |
| | 120m → 150 | 120m → 100 |
| | 150m → 150 | 160m → 100 |
| | 175m → 62 | 180m → 80 |
| | 200m → 62 | 200m → 80 |

Both members of each pair are stored, so this is the full curve, not just the ranges:
`Field_3901db14` is the distance and `Field_42fc0f5e` is the damage at that distance. That
is "minimum damage 62 → 80", "sweet spot damage 150 → 100" and "sweet spot range adjusted
to 120m to 160m", exactly.

For the site, the 1.4.3.0 `dmg` array is:

```json
[{"r": 100, "d": 80}, {"r": 120, "d": 100}, {"r": 160, "d": 100},
 {"r": 180, "d": 80}, {"r": 200, "d": 80}]
```

The existing site value is the 1.4.2.5 form of this same curve, so it is a direct
replacement. One caveat carried over from the baseline: the asset stores this curve twice,
as a point list and as a flat array, and in 1.4.2.5 the two disagreed on the fourth
distance (170 in the point list, 175 in the flat array; the site used 175). In 1.4.3.0 both
representations agree on 180, so that discrepancy is gone.

Curve `ea2b0ed0` went flat: `80/102.5/102.5/62/62` became `100` at every listed distance.
This matches "damage against armor in REDSEC increased to 100 regardless of hit location
or distance". The armour role is inferred from that wording; the list's role is not
independently decoded.

`PD_.416Barrett_Match` changed both curves the same way.

"Limb damage now matches chest damage" follows the projectile's packed material change
from **781 to 784** (`0x31005180`) and the protection arrays in both raw material grids.
A fresh bounded-reader run on 16 September reproduces headshot **1.75** at protection
index 3 and limb/abdomen **1.0** for every supported Interdictor ammo option.
The previous paragraph used scalar records at material 781; that was not the current
projectile route and must not be used to explain this change. The final trace is
`reference-data/provenance/frosty-hit-zones-2026-09-15.json`. The native lookup code has
not been disassembled; the established source mapping remains distinct from runtime proof.

"Iron Sight attachment now costs 15 points" is the `Field_6ee865a5` change above.

"Incorrect impact visual effects were corrected" is the nearest match to the blueprint's
FX changes, but those are **muzzle-flash** references, not impact effects. Two entries
that were `nullptr` gained `FX_MF_Heavy_Shape_Quad_1P/3P`, and the rest moved from
`FX_MF_Heavy_Shape_T_*` to `FX_MF_Heavy_NoMuzzleAttachment_*`. No impact-effect asset in
the captured set changed.

### SU-230 LPVO (ElcanDR)

`GCR_LPVO_4x00_1x00_P00` is bound through selector GUID
`f66c9ab7-bb18-4d2d-8133-6d90b19f0e84` in the `GS_*` assets to `WPM_SCP_ElcanDR`, the only
1-4x LPVO. The display string is `1582DFEB`, "SU-230 LPVO". The `AD_` metadata does not
carry that string id, so the link is by selector and designation rather than a decoded
name reference.

The 34 `GCR_*` camera-recoil assets form one consistent ladder. Reading the single-zoom
assets gives the value each magnification is supposed to use:

| Zoom | Value | Zoom | Value |
|---|---|---|---|
| 1.00x | -0.5 | 3.50x | 0.449399 |
| 1.25x | -0.254767 | 4.00x | 0.505185 |
| 1.50x | -0.084472 | 4.50x | 0.54968 |
| 1.75x | 0.041348 | 5.00x | 0.586081 |
| 2.00x | 0.138476 | 6.00x | 0.642258 |
| 2.50x | 0.279325 | 8.00x | 0.715803 |
| 3.00x | 0.377135 | 10.00x | 0.762266 |

The ladder is strictly monotonic in magnification. Against it the SU-230 reads cleanly:
its 4x member holds `0.505185`, the exact 4.00x value, and its other member is the 1x
state, which should hold `-0.5`.

| Member | 1.4.2.5 | 1.4.3.0 | Ladder value |
|---|---|---|---|
| 4x | 0.505185 | 0.505185 | 0.505185 (4.00x) |
| 1x (`Field_7f1bb9d4`) | **10** | **-0.5** | -0.5 (1.00x) |
| 1x (`Field_9532eb28`) | -0.5 | -0.5 | -0.5 (1.00x) |

So the defect was in the **1x state, not the 4x state**, and only in one of its two paired
fields: `Field_7f1bb9d4` held `10` where its partner already held the correct `-0.5`. A
value of 10 is far outside the whole ladder, whose maximum is 0.762266 at 10x. 1.4.3.0
sets it to `-0.5` and the two fields now agree.

Direction: the operator reports the SU-230 had far too little camera shake before the fix.
Combined with the ladder running from -0.5 at 1x up to 0.762266 at 10x, that implies a
higher value means less camera shake. On that reading the stale `10` gave the SU-230 at 1x
less shake than any legitimate optic at any zoom. The unit is still not decoded; the
direction rests on the operator's in-game observation plus the ladder's shape.

**Scan for the same defect elsewhere.** All 34 `GCR_*` assets were checked for the pattern:
paired override fields disagreeing, mismatched enable flags, or an active override outside
the ladder's range. **The SU-230 was the only asset flagged in 1.4.2.5, and it is clean in
1.4.3.0.** Every other optic's members sit exactly on the ladder value for their
magnification, including the multi-zoom LPVO, magnifier, variable and SVO families. No
other optic currently has lower camera shake than its magnification calls for.

## Limits

1. 148 changed assets have no baseline XML, so only the byte change is established and
   no old decoded value exists. These include every `MUT_*` level and game-mode tweakable,
   `KST_*` killswitch set and `GRX_*` remixer asset in the change set. Old raw EBX is
   retained. Missing XML does not by itself prevent descriptor-based decoding; those
   comparisons remain pending where no validated decoded result was recorded.
2. The two `materialgrid_win32` grids were read with the bounded reader instead of XML
   export, which has previously exhausted machine memory. Results are in
   `material-grid-inventory-1.4.3.0.json`.
3. `TweakablesConfig`, `GlacierGameConfiguration/settings` and the 24 `*_valueregistry`
   assets each changed by thousands of lines. They are aggregates whose ordering and ids
   move every build; they have not been reduced to value-level changes yet.
4. Resolved. The 248 attachment metadata assets are decoded above.
5. Unnamed fields above are labelled "unnamed" on purpose. No new field-name mapping was
   generated from this build.
6. The SDK cannot be regenerated locally (EA anticheat). Frosty's own XML export is
   therefore still incomplete for this build and will stay so; use
   `scripts/frosty-ebx-decode.py` for anything touching the 341 affected assets. Frosty
   remains correct for the other 494, and its output was the reference used to validate
   the new reader.
7. 14 of 400 validation assets decode differently from Frosty because their type name has
   more than one layout entry in the descriptors. The new reader follows the layout the
   asset declares; Frosty follows the SDK's. Such objects are tagged `$layoutAmbiguous`.
   Which is correct per asset is not settled, so treat tagged objects as provisional.
   All 27 saved PiP comparisons carry this warning. Their apparent numeric equality
   does not prove unchanged aiming behavior. The 16 September decoder correction also
   propagates warnings from nested and inherited layouts.
8. The two `materialgrid_win32` grids were read with the bounded reader, not XML. Two new
   record types are unnamed, so some per-entry type labels may be reader artefacts.
